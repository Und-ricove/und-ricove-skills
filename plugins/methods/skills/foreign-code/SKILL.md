# Работа с чужим кодом

Консервированный опыт 21–22.08.2026: форк плагина Tags Routes (MIT, © 2024 kctekn)
под себя — русификация интерфейса, динамическая пульсация связей, halo-линии,
удаление лишних органов управления. Полтора десятка итераций, из них **шесть ушли
на ошибки, каждая из которых имеет общее правило**. Скилл существует, чтобы эти шесть
не повторились на органах кукол, на LM Studio и на всём, что придётся дорабатывать.

---

## Закон нулевой: лицензия читается до первой строки кода

**Перед заимствованием — открыть LICENSE.** Разрешительные (MIT, Apache, BSD)
позволяют брать код в закрытый продукт при сохранении копирайта. **GPL «заразна»:**
включение GPL-кода обязывает открыть весь производный продукт. **AGPL строже** —
открывать нужно даже при доступе по сети.

Один GPL-компонент лишает компанию права держать свой код закрытым.
Правило: **GPL и родственные избегать всегда.**

При форке файл `LICENSE` копируется рядом с производной работой, а в `FORK.md`
записывается: что изменено, где живут исходники, как пересобрать.

## Правило 1. Править исходники, а не собранное

**Первая версия правок ушла в `main.js` — минифицированный бандл на 2,6 МБ.**
Работало, но обречено: при первом же обновлении плагина всё слетает,
а найти своё в минифицированном коде через месяц невозможно.

**Правильно:** клонировать исходники, править их, собирать. Правки переживают
пересборку и читаются как код, а не как археология.

**Правки оформляются скриптом, а не руками.** Скрипт `ru.py`, `lab_*.py` — это
воспроизводимая инструкция: взял свежую версию апстрима, прогнал, получил свой форк.
Ручная правка исходников — такая же одноразовая вещь, как правка бандла.

## Правило 2. Одна библиотека — одна версия в дереве

**Симптом:** `THREE.WARNING: Multiple instances of Three.js being imported`,
следом `TypeError: object.matrixWorld.determinantAffine is not a function`.
Граф просто не рисовался.

**Причина:** в `package.json` стояло `"three": "^0.169.0"` и `"3d-force-graph": "^1.74.1"`.
За год граф ушёл на 1.80 и потянул **свою** копию three 0.185. Объекты создавались
одной версией, рендерились другой.

**Диагностика — одной командой:**

```bash
find node_modules -type d -name <библиотека>
```

Больше одной папки — конфликт.

**Лечение:** выровнять версии и запретить расхождение:

```json
"dependencies": { "three": "0.185.1" },
"overrides":    { "three": "0.185.1" }
```

⚠️ **Направление выравнивания определяется по коду, а не по package.json.**
Я сначала понизил граф до старой версии — сборка упала на `ForceGraph3D only refers
to a type`. Подсказка нашлась в истории апстрима: коммит «Adapt to new version lib» —
**код уже был переписан под новую библиотеку, а package.json забыли обновить.**
Значит поднимать надо зависимость, а не понижать потребителя.

**Косвенное подтверждение победы:** бандл похудел с 3,93 до 3,49 МБ — ровно
на вторую копию библиотеки.

## Правило 3. Сохранённые настройки перекрывают код

**Самая обидная ошибка сессии: три итерации правок «не давали изменений».**
Палитра и фон правились в исходниках, собирались, устанавливались — а узлы
оставались зелёными.

**Причина:** пресет из кода применяется **один раз**, при первом создании настроек.
Дальше приложение читает `data.json`, и код на него не влияет вовсе.

**Правка самого файла настроек не спасает, пока приложение запущено:** при выходе
оно перезапишет файл своим состоянием из памяти.

**Правильно — миграция в коде** с отметкой версии:

```ts
export const LAB_PALETTE_VER = 2;
export function labMigratePalette(settings: any): boolean {
	if (settings.labPaletteVer === LAB_PALETTE_VER) return false;
	// ... перезаписать нужное ...
	settings.labPaletteVer = LAB_PALETTE_VER;
	return true;
}
```

Отработает один раз и не будет мешать ручным настройкам дальше.

⚠️ **Мигрировать надо все слоты, включая рабочую копию.** В том случае была
структура `dark[] / light[] / customSlot[]`, где `customSlot` собирается из слота
**до** миграции и именно из него рисуется картинка. Пройди только по темам —
правки снова не доедут до экрана, и пойдёт четвёртый круг.

## Правило 4. Не подставлять константы в код — задавать значения данными

**Каскад на ровном месте.** Убирая переключатели, я подставил в код `true`/`false`
вместо чтения настроек. TypeScript увидел `if (true)`, объявил ветку `else`
недостижимой и **сузил там типы до пустых** — посыпались `TS18048: possibly undefined`.
Каждая исправленная ошибка обнажала следующую мёртвую ветку. Четыре захода впустую.

**Правильно:** органы управления убрать из интерфейса, а значения выставить
в миграции настроек. Логика не тронута, код валиден целиком, переключить
режим пользователь всё равно не может — управления нет.

**Общий принцип:** правка данных безопаснее правки потока управления.

## Правило 5. Инструмент правки обязан быть идемпотентным

**Запустил импорт дважды ради вывода `head` и `tail` — получил 256 файлов вместо 128.**

Любой инструмент, который пишет файлы, должен помнить сделанное:

```python
known = existing_by_source(target)   # источник → адрес
if src in known:
    addr = known[src]                # обновляем на месте
else:
    addr = next_free()               # заводим новый
```

Проверка после починки: второй прогон печатает «новых 0, обновлено 128».
Тест на идемпотентность добавляется в самопроверку.

## Правило 6. Разбор структурированных форматов — не regex

**Парсер frontmatter на регулярных выражениях соврал дважды за один день:**
сперва «потерял» атом со знаком кавычки при подсчёте (257 вместо 258), потом показал
его же как непокрытый. **Данные были целы оба раза** — врал прибор, причём именно
на тех знаках, которые сам же и экранирует.

YAML, JSON, TOML читать их разборщиками. Regex — только для черновой разведки,
и любой его результат в отчёте помечать как оценку.

## Правило 7. Многострочный код не передавать через heredoc

**Три раза за сессию** bash-heredoc съел экранирование, и в файл ушёл реальный перевод
строки вместо `\n`. Один раз это сломало собранный плагин, дважды — скрипты правки.

**Правильно:** писать скрипт файлом (инструментом Write), потом запускать.
Heredoc годится для трёх строк без экранирования и ни для чего больше.

---

## Правило 8. Чинить причину, а не симптом

Три случая из одной сессии, все одного вида:

| Симптом | Ложный ход | Настоящая причина |
| --- | --- | --- |
| Граф не рисуется | «обращение к this.Graph до присвоения» | две версии Three.js |
| Частицы чёрные | «поднять яркость цвета» | `MeshLambertMaterial` требует освещения, а его нет |
| Всё белое пятно | «уменьшить силу свечения» | аддитивные линии складываются за единицу, рендер обрезает |

**Признак симптоматического лечения:** правка не убирает проблему полностью,
а сдвигает её. Если после двух попыток симптом жив — гипотеза неверна,
и надо искать источник, а не крутить коэффициент.

## Правило 9. Прежде чем усложнять — проверить штатный путь библиотеки

Я сделал восемь материалов ради прозрачности связей по ступеням. Оказалось,
у библиотеки прозрачность передаётся **прямо в цвете** как `rgba(...)`, кладётся
в вершинные цвета, и материал на все две тысячи связей остаётся **один**.
Своё решение было и дороже по кадру, и сложнее по коду.

**Порядок:** сначала прочитать, что библиотека умеет сама; своё писать,
когда штатного пути нет.

## Правило 10. Сеттер чужого класса может быть дорогим — прочитать его до вызова в цикле

**Фризы графа при движении мыши (22.08.2026).** Цикл подсветки на каждый ховер
ставил всем узлам `sprite.textHeight = 0`, затем `18` — «дёшево, это же число».
Оказалось, **каждый сеттер SpriteText, включая textHeight, перерисовывает
canvas-текстуру** (`_genCanvas`). Сотни подписей × два присвоения × каждое
движение мыши = перерисовка сотен текстур на кадр. Это и были «фризы».

Той же природы: умножение чужих значений. Библиотека сама умножала нашу альфу
из rgba-цвета на свой `linkOpacity` (0.2 по умолчанию) — вся динамика
прозрачности стиралась, и выглядело это как «правка не применилась».

**Правило:** прежде чем дёргать свойство чужого объекта в горячем цикле —
открыть его сеттер и цепочку применения. Присвоение может оказаться операцией,
а значение — сомножителем в чужой формуле. Дорогое свойство выставляется
один раз при создании; в цикле переключается только дешёвое (`visible`).

## Порядок работы над форком

1. **Лицензия** — прочитать до всего остального.
2. **Клонировать исходники**, не трогать бандл.
3. **Проверить дерево зависимостей** на дубли ключевых библиотек.
4. **Правки оформить скриптами**, чтобы переживали обновление апстрима.
5. **Собрать**, проверить не глазами, а поиском по бандлу: попали ли строки,
   есть ли новые символы, одна ли версия библиотеки.
6. **Установить**, сохранив бэкапы каждого состояния (`.orig`, `.before-<правка>`).
7. **Записать `FORK.md`**: что изменено, где исходники, как пересобрать,
   что делать, если сломается.
8. **Закоммитить** и форк, и хранилище.
