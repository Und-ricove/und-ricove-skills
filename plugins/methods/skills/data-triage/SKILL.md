# Сортировка повреждённых данных

Консервированный опыт 01–02.08.2026: разбор больших архивов данных после копирования на Linux параллельно с очисткой источника. 597 подозрительных файлов, из них 223 оказались ложным срабатыванием **моей же проверки**. Скилл существует, чтобы эти грабли не наступались заново.

## Главный закон

**Целостность файла определяется не тем, читается ли он, а тем, то ли в нём содержимое.**

Три уровня, и каждый следующий ловит то, что пропустил предыдущий:

1. **Формат** — размер, сигнатура, нулевые байты.
2. **Тип** — текст ли там, где ожидается текст.
3. **Смысл** — тот ли это текст. *Самый пропускаемый уровень.*

Пример из практики: `conversations.jsonl` весил 23 002 байта, начинался валидным текстом и прошёл первые два уровня. Внутри оказался **список рекламных доменов** вместо разговоров. Файл был перенесён в целое тело как ценный — и пойман только на третьем проходе.

## Типичная картина «копирование с гонкой»

Если источник очищался/размонтировался во время копирования, получается характерный почерк:

- **метаданные целы** — имя, размер, дата совпадают с оригиналом байт в байт;
- **содержимое подтянуто из освобождённых кластеров** — куски чужих файлов;
- в текстовых файлах всплывают `MZ`, `PE`, `This program cannot be run in DOS mode`, `System.Runtime`;
- либо блоки нулевых байтов;
- либо валидный, но **посторонний** текст.

Одинаковый размер + одинаковая дата + **разный MD5** — самый надёжный признак этой аварии. Сравнение по датам здесь бесполезно и обманет.

## 🔴 Ловушка, стоившая 223 файлов

**Сигнатура `MZ` в начале файла — это норма для `.dll`, `.exe`, `.pyd`, `.sys`.** Это PE-заголовок Windows, а не повреждение.

Критерий «начинается с MZ → битый» применять **только к файлам, где ожидается текст**. Иначе выносятся рабочие библиотеки (в тот раз — весь LibreHardwareMonitor).

Аналогично нулевые байты: для `.png`, `.gguf`, `.sqlite`, `.zip` они законны.

**Расширения, которые нельзя судить текстовыми критериями:**
`.dll .exe .pyd .so .sys .zip .gz .7z .tar .enc .gguf .safetensors .bin .pt .onnx .png .jpg .gif .ico .webp .glb .gltf .pyc .pdf .ttf .woff .mp3 .mp4 .db .sqlite .lance .npy`

Для них единственный валидный текстовый критерий — **нулевой размер**.

### 🔴 Но и нулевой размер сам по себе не улика

**Опыт 16.08.2026.** Скан архива на 44 тысячи файлов дал десять нулевых — и **все десять
оказались нулевыми по назначению**:

- `__init__.py` — обязательный пустой маркер Python-пакета;
- пустые логи — процесс просто не писал;
- `*_err.txt` — файлы для потока ошибок, пустые именно потому, что ошибок не было.

**Правило:** прежде чем нести нулевой файл в карантин, спроси, **должен ли он что-то
содержать**. Пустота по контракту — не повреждение. Правило работает в обе стороны:
ненулевой размер не доказывает целостность, нулевой не доказывает порчу.

### Сверка дублей: три уровня, а не «одинаковые имена»

Прежде чем удалить «дубль», проверять по возрастанию строгости:

1. **Сигнатура** — файл действительно того типа, за который себя выдаёт (`MZ` у библиотеки,
   а не переименованный архив с данными). Это отсекает подмену размера.
2. **SHA-256 отдельных файлов** — побайтовое совпадение.
3. **Агрегированный хэш дерева** — для папок: собрать хэши всех файлов, отсортировать,
   свернуть в один. Совпал — папки идентичны по содержимому, а не только по числу файлов.

```bash
find "папка" -type f -exec sha256sum {} \; | sed 's| .*/| |' | sort | sha256sum
```

Именно так 16.08.2026 подтверждались дубли перед удалением 3,9 ГБ: две копии
по 115 файлов дали один агрегированный хэш, и только после этого одна была снята.

## Порядок работы

### 1. Бэкап до всего

Никакой диагностики до бэкапа. Но сначала **измерить, что именно бэкапить**: обычно 95 % объёма — это рантайм-кэш и веса моделей, которые восстанавливаются, а ценное весит копейки.

```powershell
Get-ChildItem <корень> -Directory | ForEach-Object {
  $s = Get-ChildItem $_.FullName -Recurse -File -EA SilentlyContinue | Measure-Object Length -Sum
  "{0,-24} {1,6} файлов {2,8} МБ" -f $_.Name, $s.Count, [math]::Round($s.Sum/1MB,1)
}
```

В том разборе архивы весили 2,2 и 9,7 ГБ, а **вся ценная часть — 60 МБ**: снимки, состояние, ядро памяти, личные разделы. Копирование заняло секунды.

Копировать с исключением тяжёлого:
```powershell
robocopy <src> <dst> /E /XD __pycache__ .venv node_modules .git /XF *.pyc /NFL /NDL /NJH /NJS
```
Коды возврата robocopy 0–7 — это успех, не ошибка.

### 2. Диагностика

Функция-вердикт (Python, устойчивее PowerShell на больших деревьях):

```python
BINARY_EXT = {".dll",".exe",".pyd",".so",".zip",".gz",".enc",".gguf",".safetensors",
              ".bin",".png",".jpg",".ico",".glb",".pyc",".pdf",".ttf",".db",".sqlite",".npy"}

def verdict(p):
    size = p.stat().st_size
    if size == 0:
        return "пустой"
    head = p.open("rb").read(8192)
    if p.suffix.lower() in BINARY_EXT:
        return None                      # бинарь ненулевого размера — не судим
    if head[:2] == b"MZ":
        return "исполняемый код вместо текста"
    if b"\x00" in head:
        return "нулевые байты в текстовом файле"
    return None
```

Читать **8 КБ, а не 512 байт**: повреждение часто начинается не с начала файла (в том разборе первый нулевой байт стоял на позиции 4101).

### 3. Проверка смысла — обязательная, не опциональная

Для каждого файла, прошедшего формальные проверки, **посмотреть первые 150–300 символов глазами**. Совпадает ли содержимое с именем и назначением? Это единственный способ поймать подмену валидным чужим текстом.

### 4. Поиск доноров

Прежде чем объявлять потерю — искать целые копии по всей машине:

```powershell
Get-ChildItem <корень поиска> -Recurse -File -Filter '<имя>' -EA SilentlyContinue
```

Совпадение размера байт в байт при целом содержимом = донор найден. В том разборе так нашлись целые копии почти всего: сборка одного проекта содержала невредимые версии файлов, битых в другом.

### 5. Карантин, а не удаление

Переносить в отдельную папку **с сохранением структуры путей**, писать манифест: что вынесено, почему, есть ли донор. Ничего не удалять до подтверждения, что система работает без этих файлов.

**🔴 Усиление правила (пользователь, 10.08.2026). Карантин обязателен даже тогда, когда файл заведомо не нужен:** донор найден, ссылок нет, содержимое бесполезно. Соблазн отправить такой файл в Корзину как «очевидный мусор» — ошибка порядка, и она уже была допущена.

> **Битый файл — улика, а не мусор.** Ценность в нём не содержимое, а ответ на вопрос: *что происходило с системой, раз файл оказался битым.*

Один и тот же обрезанный файл означает три разные вещи, и различить их можно только расследованием:

- **сбой носителя** — обрыв по границе блока (512, 4096), рядом другие пострадавшие;
- **гонка при копировании** — файл есть в источнике целым, хеши расходятся, даты совпадают;
- **брошенный черновик** — в источнике файла нет вовсе, обрыв посреди слова, хеш с рождения не менялся.

Третий случай к целостности данных отношения не имеет: паниковать и звать `chkdsk` не о чем. Но узнать это можно **только** после расследования — а расследовать нечего, если файл уже в Корзине.

**Минимум, который записывается по каждому делу:** размер и SHA-256 · чем обнаружено · когда файл появился и менялся ли (git) · есть ли он в источнике · донор по имени и по функции отдельно · вывод о природе · что предлагается.

**Донор по функции ≠ донор по имени.** Файл может быть невосполним по имени и при этом полностью замещён соседом с другой реализацией той же задачи. Это разные выводы: первый означает потерю, второй — что терять нечего.

## Специальные проверки

**SQLite:** первые 15 байт должны быть `SQLite format 3`. Нулевой размер = база уничтожена.

**LanceDB:** целостность живёт в `*.manifest` внутри `<таблица>.lance\_versions\`. Проверять их массово на `MZ` — если там PE-заголовки, таблица не откроется. Целая база: тысячи манифестов, повреждённых ноль.

**Зашифрованные архивы:** если рядом лежит манифест с SHA-256 — **проверять хеш шифротекста, не расшифровывая**. Ключ для этого не нужен, а результат говорит, восстановим ли архив вообще.

**Кодировка:** повреждение и не-UTF-8 — разные болезни со схожими симптомами. Файл в cp1251 читается как мусор, но данные целы и конвертируются. Если стандарт проекта UTF-8, а часть файлов в другой кодировке — это отдельная находка, не повреждение. Проверять через `/encoding-check`, чинить конвертацией, а не карантином.

## Чего не делать

- **Не сливать две ветки по датам изменения.** При этой аварии даты идентичны у целого и битого. Только хеши.
- **Не доверять «файл открылся».** См. главный закон.
- **Не удалять безвозвратно.** Только в карантин или в корзину (`Shell.Application` → `InvokeVerb('delete')`).
- **Не чинить диск рефлекторно.** Если причина установлена (гонка при копировании, сбой миграции), `chkdsk` не нужен. Проверить `Get-PhysicalDisk | Select HealthStatus` — 30 секунд, и хватит.

## 🔴 Правило 15% — не верить своему же массовому проходу

**Пользователь, 17.08.2026.** Массовая проверка (хеши, сигнатуры, регулярки по тысячам
файлов) сверяется руками на **5% в начале, 5% в середине и 5% в конце** списка —
глядя в сами файлы, а не в свой отчёт. Три окна ловят разное: настройку инструмента,
метод на типичном материале, обрывы в хвосте.

Здесь это особенно дёшево и особенно нужно: цена ошибки триажа — либо потерянный
целый файл, либо принятый за целый битый. Полностью правило — в `number-forensics`.

## Итог, который надо доложить

1. Сколько проверено, сколько повреждено, **сколько ложных срабатываний** — свои ошибки называть первыми.
2. Какое хранилище признано источником истины и почему.
3. Что восстановимо из доноров, что потеряно безвозвратно.
4. Куда вынесен карантин и когда его можно будет удалить.
